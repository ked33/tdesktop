# 视频播放器开关时的聊天位移诊断

绘制入口发现待重排消息时，现在调用完整的历史几何更新，在同一次更新中
完成布局和锚点滚动补偿；更新期间的绘制重入不会重复启动更新。保留原有的
首次加载、窗口动画、底部跟随和必要重排策略。

诊断辅助代码位于 `Telegram/SourceFiles/test/test_video_scroll.cpp`，只观察状态，
普通云构建也会包含，不需要 `-testagent` 或本地 Debug 构建。

## 使用

1. 安装包含此改动的 GitHub Actions 构建。
2. 开启“设置 → 增强设置 → 网络 → 将在线播放调试日志写入 log.txt”。
3. 完全退出并重新启动客户端，打开原聊天中间位置的视频 A，观察位移后关闭。
4. 关闭后等待约 25 秒，再打开、关闭同一个 A；最后再等待约 25 秒。
5. 查看现有 `log.txt` 中以 `Video Scroll:` 开头的行。便携版通常位于程序目录。
   保留首轮异常和第二轮正常的完整记录，随后关闭上述日志开关。

启动或切换日志开关时，`config version=2 enabled=1` 表示新版诊断已开启；
`enabled=0` 表示当前关闭。缺少该标记不能当作“没有发生滚动”。

不要求视频能够自动播放。捕获从手动激活视频点击处理器开始；`open-dispatch`
标记进入打开文档调用，随后记录播放器显示、共享播放器锁定、清理和关闭。
当前入口覆盖普通聊天的 `HistoryInner`，其他消息列表入口不在本次捕获范围内。

## 节流与范围

- 每次启动最多捕获 8 轮视频操作，`cycle` 区分各轮；`cyclesLeft=0` 后需要重启。
- 打开和关闭各观察 15 秒。打开窗口过期后停止采样，稍后关闭时重新观察 15 秒。
- 开启日志期间，内存保留最近 30 秒、最多 1024 项重排来源，合并近期相同来源。
  它覆盖点击前已标记、到播放器打开后才处理的更新；`causesEvicted` 标记容量淘汰。
- 每次布局更新前后比对最多 4096 条已加载消息，不仅是被点击的视频。
  对比消息、媒体、最优尺寸、声明和实测视频尺寸、位置及视图替换。
- 同类事件的相同状态在 250 毫秒内合并；状态变化不按重复事件丢弃。
- 每 250 毫秒最多写 24 条普通事件，每个阶段最多 96 条；边界和汇总另计。
- 尺寸证据独立保留，每阶段最多 192 条，以每次 250 毫秒采样最多 8 条的速度输出。
- 实际滚动、请求／应用滚动、补偿目标／出口及播放器事件另保留每阶段 96 条额度，
  与尺寸证据共享上述输出速度；汇总中的 `transitions` 是该类记录数量。
  `buffered=1` 的 `t` 是采集时间，文件中的输出顺序可能滞后；分析时按 `cycle`、
  `t` 和 `layout` 关联。阶段结束后会继续排空缓冲，关闭播放器不会清空打开阶段证据。
- 汇总中的 `duplicates` 是合并数量，`limited` 是达到上限后省略的数量。
  限流时额外保留首条、末条省略事件及实际滚动位置范围，不把“没日志”当成“没发生”。
- `queued` 表示汇总时尚未写出的证据。新一轮点击或聊天销毁会结束旧观察器；
  未排空时记录 `evidence-abandoned` 及首末条证据。等待 25 秒有助于保留完整记录。
- `cycle-limit` 表示本次启动已用完 8 轮捕获，需要重启客户端。
- 定时采样每 250 毫秒检查一次，仅状态变化时记录；同步观察点用于保留短暂位移。
- 不记录消息正文、联系人名称、媒体地址或凭证。会记录消息及文档数字 ID。
- 上述上限只约束 `Video Scroll:`；同一开关启用的已有播放日志沿用原有节流。

## 主要字段

| 字段或事件 | 含义 |
| --- | --- |
| `cycle` / `phase` / `t` | 操作编号、打开或关闭阶段、距本轮开始的毫秒数 |
| `scroll` / `max` / `over` | 实际滚动位置、最大位置、弹性越界距离 |
| `viewport` / `list` | 视口和列表的本地几何信息：x、y、宽、高 |
| `listGlobalY` / `screenY` | 列表原点、目标消息顶部的屏幕坐标 |
| `historyTop` / `top` | 聊天内容起点、目标消息顶部在列表中的位置 |
| `anchor` / `migrated` | 当前／迁移前历史的锚点消息 ID、偏移、历史高度 |
| `savedTop` | 锚点推导的滚动位置；无有效锚点时为 -1 |
| `message` / `media` / `optimal` | 当前消息尺寸、当前媒体尺寸、媒体最优尺寸 |
| `pending` / `viewPending` | 历史和目标消息是否等待重排 |
| `cause` / `kind` / `source` | 更新种类、调用文件、行号和函数；不一定来自点击的视频消息 |
| `row-change` / `row-added` / `row-removed` | 实际发生尺寸或视图变化的消息；含变化前后状态和近期来源 |
| `row-observed` / `row-unobserved` | 快照达到条数上限时的覆盖变化，不能确定为新增／删除 |
| `dh` / `dy` / `replaced` | 消息高度变化、顶部位置变化、视图对象是否替换 |
| `layout-diff` | 一次前后对比的汇总；`pass` 区分布局内、布局前及定时采样 |
| `heightDelta` / `rowHeightDelta` | 历史总高度变化与各消息高度变化之和 |
| `unmatchedDelta` / `skipped` | 未被逐条尺寸解释的高度差、快照未覆盖的消息数；非零时不要强行归因 |
| `causes` | 最多 4 条消息来源和 2 条历史级来源；负时间表示点击前；`unobserved` 表示没有近期记录 |
| `causeMsg` | 内嵌视频尺寸或播放状态观察点对应的消息 |
| `inline-optimal` / `inline-current` | 本次媒体尺寸计算结果 `size`；`value` 是活跃内嵌流是否存在，`frame` 是用于计算的帧尺寸 |
| `inline-ready` / `inline-stop-*` | 内嵌流就绪和清理过程；并不表示用户开启了自动播放 |
| `geometry-enter` | `value` 为 `_topDelta`，`extra` 为滚动补偿类型 |
| `geometry-state` | 初始更新、加载、动画、初始化完成、待更新及重入状态 |
| `geometry-policy` | `value` 为原先是否在底部，`extra` 为视口是否需要改变尺寸 |
| `geometry-initial` / `geometry-bottom` / `geometry-anchor` | 实际选择的定位策略及钳制前目标位置 |
| `geometry-skip-*` / `geometry-defer-*` | 未执行完整更新的原因：初始化条件、无可用高度、动画或首次加载 |
| `geometry-target` | `value` 为目标位置，`extra` 为本次滚动补偿量 |
| `geometry-exit` | 更新返回时的状态；`value` 为是否仍需更新，`extra` 为是否仍在外层更新 |
| `scroll-request` / `scroll-applied` | 请求滚动与调用完成后的状态，`value` 为请求位置 |
| `scroll-middle-click` / `scroll-selection` | 中键或选区的定时滚动请求 |
| `scroll-keyboard-focus` / `scroll-accessibility-focus` | 显式聚焦逻辑检查的目标区域，是否滚动须结合后续实际事件 |
| `widget-event` | 窗口／视口／列表移动、尺寸变化、焦点和输入事件；不记录按键内容 |
| `paint-layout` / `paint-layout-reentrant` | 绘制入口启动完整更新，或因已有更新而跳过重入 |
| `anchor-skipped-pending` | 因待重排而跳过保存当前锚点 |

先对比 `screenY`、`scroll` 与 `listGlobalY`，再沿同一轮的采集时间寻找首次变化。
观察点可能位于一次布局更新的中间，因此应连同后续 `list-size-after`、
`scroll-applied` 和阶段汇总一起判断，不能单凭一条中间状态认定根因。

历史中间位置的预期是：上方消息高度变化时，目标消息 `top` 和实际 `scroll`
在本次更新结束前变化相同的量，`screenY` 保持稳定。例如上方缩短 538 像素，
`top` 和 `scroll` 均应减少 538，而不是等关闭播放器后的另一次更新才补偿。
单条 `causes` 只是近期调用来源；需要结合对应消息的 `dh`、批次高度差和锚点
才能确定因果关系，不能把所有变化归到最后一条视频尺寸日志。
