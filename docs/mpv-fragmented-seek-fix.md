# MPV 分片 MP4 的缓存外跳转

没有全局索引的分片 MP4 按目标时间准备跳转入口，避免每次首次远跳都等待全文件元数据扫描。本次修复进一步保留缓存外反向跳转的原始目标，避免 MPV 已返回旧分片起点后被误判为跳转成功。首播继续使用快速打开选项，普通 MP4 的 Range、大文件头和多 `mdat` 支持保持有效。

## 原因

用户提供的 `log - db21ec8.txt` 与 `mpv - db21ec8.log` 表明，后台元数据扫描仍明显落后于播放器读取。上一版虽然恢复了首播，却依然需要扫描全部分片后才能可靠跳到未缓存位置。Telegram 按块下载，因此只保存少量元数据也可能需要读取分散在整个文件中的许多远程块。

样本 `100.mp4` 为 310,189,901 字节，包含 338 个 `moof` 和 338 个 `mdat`，没有 `sidx` 或 `mfra` 全局索引。音频和视频通常分开存放在相邻分片中，文件开头还有空轨道分片。

## 实现

1. 初始播放继续使用 `ignore_editlist=1,fflags=+ignidx`。独立 Reader 读取轨道信息与少量初始分片，保留各轨的时基、默认采样参数和分片位置。
2. 缓存外跳转时，利用目标时间和已知文件位置估算探测点，读取附近的 `moof`，解析 `tfdt`、`tfhd`、`trun`。视频定位考虑首帧的呈现时间偏移，选择可独立解码的分片，并同时定位音频。
3. 每个跳转结果使用独立的 `?tdesktop_index=<revision>` URL。在这一固定视图中，把第一个 `moof` 的前 16 字节输出为一个 64 位长度的 `free` atom，让解复用器直接跳到所有轨道所需的最早分片。其余媒体字节、文件总长度和媒体偏移都保持原值，磁盘原文件不变。
4. MPV 在同一进程重新打开这一视图，仍使用快速打开选项，从目标附近建立局部采样索引并恢复准确时间和暂停状态。后续分片可以继续顺序读取，不需要补造全局索引。
5. 新目标可以取代尚未完成的定位；已经正常完成的缓存内跳转会取消多余工作。最多保留 8 份跳转视图，正在发送的 HTTP 响应持有自己的固定快照。
6. 首次按需重载前临时启用 MPV 的 idle，避免等待定位时播放器因 EOF 退出。结束控制或切换文件时恢复原值；用户的 `keep-open` 设置不变。暂停状态区分用户操作和 EOF 自动暂停。
7. 已有全局索引、未知时长或无法可靠解析的布局继续使用完整元数据缓存作为回退。回退仍有扫描成本；关闭播放器或切换文件会取消后台工作，Reader 在主线程停止并释放。

解析限制包括：最多 8 个音视频轨道、4 MiB `moov`、256 KiB `moof`、每轨分片合计 65,536 个采样、每次读取 64 KiB、单个探测窗口 4 MiB、每次定位读取预算 16 MiB、48 轮定位和 8,192 个缓存定位点。未知标志、无效字段和越界时间不会生成跳转入口。

- 快速连续拖动、定位期间更换目标，以及重载完成后再次跳转。
- 等待跳转时暂停或继续播放，保持用户的新状态。
- 缓存内跳转不触发重载，以及关键帧跳转。
- 已重载后切换文件、定位中关闭播放器和 Reader 主线程清理。
- 默认配置下正常播放到结尾退出，以及恢复用户的 `idle=yes,keep-open=always` 设置。

MPV 在原生打开文件的短暂窗口中会拒绝 seek，返回 `error running command`。专门的延迟打开测试确认了这一区别：被 MPV 拒绝的命令在文件可用后重试，已受理的新目标可以完成跳转；控制器无法接管 MPV 未产生 seek 事件的输入。

独立 MP4 文件头和索引测试、Smart 策略公式及 56 项结构检查通过。索引测试包含前缀边界、原偏移保持、空轨道分片、呈现时间偏移、取消、无效输入、时间溢出和读取/采样预算。索引测试已接入现有 Windows 构建检查。

## 反向跳转回归（2026-09-13）

### 日志证据与原因

`a84a5a0` 与 `f107726` 的匹配播放记录出现同一种错误：MPV 接受较早的时间目标，但当前按需视图从较晚分片开始，解复用器很快返回这一视图的最早帧。播放恢复不等于到达了用户目标。

| 日志 | 原始目标与字节定位 | 实际结果 |
|---|---|---|
| `mpv - a84a5a0.log` | 第 1048 行请求 572.003793 秒；第 1117 行按需重载 | 第 1476 行恢复到 572.000000 秒，前进成功 |
| `mpv - a84a5a0.log` | 第 1733 行请求 319.117906 秒；第 1747 行仍读取字节 212927457 | 第 1787 行恢复到 570.000000 秒，没有为原目标重载 |
| `mpv - a84a5a0.log` | 第 4419 行请求 708.481891 秒；第 4480 行按需重载 | 第 4733 行恢复到 708.480000 秒，前进成功 |
| `mpv - a84a5a0.log` | 第 5491、9649 行请求 351.230399、132.464036 秒；均读取字节 262475002 附近 | 第 5540、9706 行均恢复到 704.400000 秒 |
| `mpv - f107726.log` | 第 2638 行请求 114.400759 秒；第 2652 行仍读取字节 212927457 | 第 2692 行恢复到 570.000000 秒；随后请求 158、202、303 秒也得到相同落点 |

`log - a84a5a0.txt` 仅第 153、488 行完成 572、708 秒的索引准备；第 1059 行累计 `http_failed=0`。`log - f107726.txt` 包含两轮播放，这份 MPV 日志对应第 1450 行、11:47:13 开始的第二轮；不能把第一轮的反向索引记录混入对照。第二轮仅第 1490、1587 行完成 309、572 秒的准备，第 1899 行同样为 `http_failed=0`。这些证据指向时间目标丢失，没有显示反向 Range 下载失败；日志未记录原始 HTTP Range 响应头。

两份 MPV 日志版本均为 `v0.41.0-dev-g41f6a6450`，启用 `hr-seek=yes` 和 seekable cache；运行中的网络配置把前向缓存设为 256 MiB、后向缓存设为 128 MiB，预读 10 秒、滞回 5 秒。用户操作通常是暂停、发送 `absolute+exact`、约 50–80 ms 后继续播放。`f107726` 第 5043、5047 行还连续发送了 305.068690 秒 exact 和 303.061659 秒 keyframes，最终目标已经变化；只读取 exact 的 `hr-seek` 日志会漏掉后一次输入。

前版订阅 `time-pos`，保存 seek 后、playback-restart 前的首份属性快照，修正了查询响应来得太晚的一种情况。但 `observe_property` 通知可以合并，中间的原目标快照不一定送达。此时快照和随后查询都可能只剩 570 或 704.4 秒的错误落点，控制器把它当作用户目标并提前结束定位。仅延迟处理已排队的通知不能证明这一缺失场景已覆盖。

### 目标保留与兼容路径

按需索引可用时，控制器通过现有 IPC 订阅 debug 级日志，仅处理 `cplayer` 来源的已识别格式：

1. `Run command: seek` 保留可解析的绝对目标，识别 exact、keyframes 和绝对百分比；连续命令更新目标及序号。命令日志本身不代表 MPV 已受理或执行，不能直接据此强制重载。
2. 与当前操作关联的 `hr-seek, skipping to` 补充实际执行的准确目标。关键帧跳转可以没有这条日志，因此还关联 `playback restart complete @` 的实际落点，包含暂停状态后缀。当视图最早帧明显晚于请求目标时保留原目标；合法的原生关键帧落点和已完成的缓存内跳转继续使用原有完成判定。
3. 已确认的日志目标不会被较晚的属性响应覆盖；完成后作废在途的位置查询。重载前检查文件所有权及目标序号，连续拖动、更换文件、停止或退出不会让旧目标重新加载到新操作之上。
4. 原有 `time-pos` 订阅、异步查询、seek 和 playback-restart 路径仍然保留。相对定位、属性定位和其他无法从命令可靠还原的操作继续使用属性回退；帧、字幕等非普通 seek 操作只在能够关联执行日志时补充目标。

核心日志文本不是 MPV 的稳定 API。未知格式、未知参数或无效数值不会被猜成目标；缺少可用日志时继续走属性路径，这种兼容回退不能保证修复所有未来版本的通知合并情形。实现没有改变用户的 MPV 配置文件。

上版对大 `mdat` 探测窗口的修复仍保留：插值点和搜索上界落在同一个媒体块时，从最后确认的分片边界继续读取元数据，仍遵守读取预算和迭代上限。

## 时长与验证边界

用户样本声明时长约 844.98 秒，但逐包检查得到最后的视频帧为 834.12 秒，最后音频包约为 834.15 秒。842 秒处没有实际帧。定位可以识别已到达物理文件尾并选择最后分片，避免因声明时长偏大而退回全量扫描；这不会补出不存在的内容。正常退出测试从 831 秒播放到真实结尾。

以上延迟来自模拟冷块，不代表用户网络中的耗时。无法可靠解析的布局仍需要完整扫描，不能保证所有文件都能立即跳转。

本机没有配置好的 Telegram 完整构建树及项目依赖，未编译完整客户端，也未运行真实 Telegram Reader / MTProto 远程播放。独立 Qt 驱动和本机 HTTP 验证不能替代完整客户端的 Actions 构建、真实网络验证或可视/听感检查。
