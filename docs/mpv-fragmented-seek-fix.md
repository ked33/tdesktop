# MPV 分片 MP4 首播与缓存外 seek 修复

本次修复解决 `2027b874a3` 引入的首播黑屏回归：MP4 先快速打开，分片元数据在后台准备；需要缓存外跳转时，再使用准备好的索引。普通 MP4 的 Range、大文件头和多 `mdat` 支持继续保留。

## 根因与两次故障的区别

用户样本 `100.mp4` 大小为 310,189,901 字节，时长约 845 秒，包含 338 个 `moof` 和 338 个 `mdat`，没有 `sidx` 或 `mfra` 全局索引。

最初无法跳到未缓存位置，是因为桥接把分片文件的 Range 请求改成从头开始的 `200 OK`，MPV 因而报告 `Stream is not seekable`。恢复标准 Range 是必要修复。

随后提交同时移除了 `fflags=+ignidx`。FFmpeg 因此在首帧之前遍历全文件的分片头。用户提供的 `mpv - 2027b87.log` 和 `log - 2027b87.txt` 显示，约 39 秒后仍在扫描约 97 MB 处，尚未进入正常播放。之前无网络延迟的本机 HTTP 测试掩盖了这项启动成本。

仅恢复 `+ignidx` 可以重新快速打开，但没有全局索引的文件在缓存外精确跳转时仍可能从前面的分片持续解码，所以还需要准备索引。

## 实现

- MP4 首次打开使用 `ignore_editlist=1,fflags=+ignidx`，保留标准 `206 Partial Content`、`Content-Range`、`Accept-Ranges` 和正确的长度、偏移。
- 检测到分片布局后，以独立 Reader 遍历容器元数据，跳过 `mdat` 载荷，只保存原始元数据和数据块头。最多保存 16 MiB、处理 65,536 个根 atom，每次读取不超过 64 KiB。
- 索引 Reader 与播放使用同一下载优先级，避免 Telegram 仅调度最高优先级任务时饿死索引。新增 Metadata 读取模式只请求当前读取覆盖的块，通常为 1–2 个，不做媒体预读，也不增加 DC 的总并发限制。
- 元数据准备好以后，HTTP 响应可直接从该缓存提供分片头。MPV 正在等待跳转时，IPC 控制器在同一进程重新打开同一 URL，恢复正常索引解析，并传入当前目标时间和暂停状态。每个控制器只执行一次这样的重新加载。
- 对缺失总时长的分片文件，仅在输出中补齐未知的 `mvhd` / `mdhd` 时长，采用 Telegram 已知时长和各轨的 timescale；有效的原时长保持原值。如果没有可信的时长提示，索引准备好后可刷新一次，以获取完整时长。
- 切换到其他文件会停止旧文件的控制和索引准备；关闭播放、读取失败或索引超过上限时可取消后台工作。取消由工作线程检查，主线程清理 Reader 的通知指针后才发布结果。
- 保留普通前置大 `moov`、多 `mdat` 文件的输出头修补、独立 seek Reader、请求代次和断连取消。分片文件的 `moof` / `mdat` 边界、采样偏移与原始文件都不改写。

## 回归验证

2026-09-13 使用真实 MPV、本地 HTTP 桥接、`--cache=no` 和每个首次读取冷块 100 ms 的模拟延迟验证。视频、音频输出使用 null 后端，检查解码后的时间位置和 seek 状态。

| 文件布局 | 首播 | 5 次单次跳转 | 连续 6 次跳转的最终位置 |
|---|---|---|---|
| 普通前置 `moov` | 通过 | 通过 | 通过 |
| 3 MiB 大 `moov` | 通过 | 通过 | 通过 |
| 多 `mdat` | 通过 | 通过 | 通过 |
| 大 `moov` 与多 `mdat` | 通过 | 通过 | 通过 |
| 尾部 `moov` | 通过 | 通过 | 通过 |
| 含 `mfra` 的分片 MP4 | 通过 | 通过 | 通过 |
| 含 `sidx` 的分片 MP4 | 通过 | 通过 | 通过 |
| 无全局索引的生成分片 MP4 | 通过 | 通过 | 通过 |
| 用户样本 `100.mp4` | 通过 | 通过 | 通过 |

用户样本在上述模拟条件下约 3.16 秒完成首播，首播时索引尚未准备完成。后台保存 712,931 字节元数据，准备约 37.23 秒。首次立即跳到约 760 秒耗时约 38.90 秒；之后跳到约 127、803、338、718 秒分别约 0.97–1.41 秒。旧行为在相同冷块延迟下未能通过 5 秒首播门槛。

另外以临时 Qt 6.8.3 驱动编译并运行真实 C++ IPC 控制器，覆盖暂停、正常播放、索引准备期间连续跳转、缺失时长刷新、切换文件、关闭播放器和无需跳转的播放。检查目标位置、暂停状态及只重新加载一次；已知时长且没有跳转时不触发重新加载。

同一 C++ 控制器也通过了用户样本的独立检查：首播约 3.47 秒，随后完成约 760、127、803、338、718 秒的位置跳转，保持暂停状态，只重新加载一次。

MP4 文件头和索引缓存独立 C++ 测试通过，分别执行 43,131 和 534,445 次断言（包含逐字节边界循环，非同等数量的独立场景）。Smart 策略公式和 56 项结构检查通过。索引缓存测试已接入现有 Windows 构建检查。

索引准备模块另以替身 Reader 检查成功、等待中取消、结果发布前取消、无效输入及主线程释放；这是模块生命周期测试，不涉及真实下载。

## 成本与验证边界

无全局索引的文件仍必须读取分片元数据才能可靠定位。首次立即远跳可能需要等待后台准备；不能承诺所有视频立即跳转。缓存仅保存元数据，但 Telegram 按 128 KiB 块下载，实际网络读取量会大于保存的元数据大小。

本机 HTTP 测试不能代替 Telegram Reader / MTProto 的真实网络验证，也不代表用户网络中的耗时。布局样本覆盖此前修过的大文件头和多数据块路径，但没有拿到此前全部真实视频。

当前工作区缺少配置好的 `out` 和 Telegram 项目依赖，未在本机编译完整客户端或运行真实 Telegram 远程播放。C++ IPC 控制器的独立 Qt 编译也不能替代完整客户端构建。

## 复现命令

先编译独立测试目标 `test_mp4_header` 和 `test_mp4_index`，再从仓库根目录运行：

```bash
python Telegram/SourceFiles/test/test_mpv_seek.py   --mpv "D:/D-Software/mpv-hero/mpv.exe"   --ffmpeg "D:/D-Software/yt-dlp/ffmpeg.exe"   --header-test "out/Debug/test_mp4_header.exe"   --index-test "out/Debug/test_mp4_index.exe"   --sample "D:/D-Download/100.mp4"   --latency-ms 100
```

脚本生成布局样本并记录日志、HTTP 请求、冷块读取和 `summary.json`。`--previous-behavior` 使用首播前完整扫描索引的旧选项作对照，`--skip-fixtures` 只检查指定样本。这个脚本通过 Python 发送索引升级命令；实际 C++ 控制器的检查是上述单独的 Qt 驱动测试。
